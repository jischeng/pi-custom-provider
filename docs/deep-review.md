# 原生 TUI 与程序接口复审

日期：2026-09-21。基线：`e8329fa`，Pi 0.82.0。

## 范围与原生界面结论

检查了基线实现、本次未提交改动、公共 Pi 接口和相关测试。当前改动此前没有拆成多轮 Git 提交，因此不能把讨论中的每次修改当作独立提交。

截图来自旧版自绘向导：基线 `src/wizard.ts` 的 208、275、309、312 行分别包含横线、按键提示、Providers 和 Create New Provider，基线入口调用 `ctx.ui.custom`。当时个人 Pi 配置加载的是主目录 `/Users/d4rw1nz/dev/ai/pi-custom-provider`，新实现位于另一个 Git 工作区，尚未影响该界面。

本次删除旧向导和对应状态机。新 `src/ui.ts` 只使用 Pi 的 `select/input/editor/confirm/notify/setStatus`，没有自绘组件、ANSI 输出或自定义按键处理。主分支合并后，需要在 Pi 中重新加载扩展或重启，以替换已加载的旧代码。

## 发现和修正

| 问题及证据 | 影响 | 最终处理 |
| --- | --- | --- |
| 构建配置时先展开旧对象，`unset` 回归测试证明 name、compat 被恢复 | 无法明确清除字段 | 从已校验的公共字段重建配置，仅明确保留私有认证字段 |
| 草稿保存跨文件锁等待仍持有可变草稿；等待期间编辑的测试失败 | 保存内容与用户确认的版本不一致 | 保存不可变快照，并在锁内检查草稿版本 |
| 发现、选择、手动修改模型各自修改草稿；非法发现结果和候选同步测试失败 | 无效数据先进入草稿，旧候选可能恢复已清除字段 | 所有修改统一走 updateDraft，完整校验成功后替换；目标变化清除旧候选 |
| 一次性写入创建临时草稿；100 个草稿和过期容量测试失败 | RPC 写入受到无关编辑会话限制 | 直接写入直接保存；创建草稿前统一回收过期项 |
| OAuth 只在开始前校验配置版本；登录期间更换地址的测试失败 | 迟到的登录结果仍写入已失效配置对应的凭据 | 登录先取得结果，在配置锁内再次核对版本，再保存凭据 |
| 空文件用 `raw || "{}"` 处理，写入未统一校验根类型 | 损坏的认证文件被覆盖 | 区分不存在与空文件，读写共享严格解析；实际写入后才记录副作用 |
| 外部 OAuth 文件读取与写回选择不同位置，且保留旧 token 别名；测试出现两次刷新 | 刷新后仍读取过期令牌 | 共享凭据定位函数，更新同一位置和已存在的别名，保留无关内容 |
| UI 通过 lastResult 间接判断保存，认证选项又单独维护 | 结果依赖隐藏状态，界面可能提供无效选项 | 保存直接检查该次操作结果；界面与 RPC 共用目录返回的认证值 |
| 额外暴露 Pi OAuth 登录入口会形成第二个凭据写入位置 | 登录和清除可能操作不同凭据 | 认证统一通过管理操作完成，运行时只读取和刷新同一绑定 |
| 通用任务保存结果对象引用，并按创建时间过期 | 插件后续修改会改变历史结果，长任务刚完成就可能过期 | 结果与事件分别复制，保留期从完成时间计算；新增独立回归测试 |

这些修改集中到配置构建、草稿更新、保存和认证写入几个共同入口，没有为每个调用方增加独立补丁。RPC 直接使用业务操作，不运行终端向导、不让模型代为执行；TUI 与模型工具复用同一组业务规则。

## 启动错误跟进

合并后用户报告启动时出现“配置字段不符合要求”。只读检查定位到两个供应商、四个模型的 `compat.supportsAdditionalTools`。Pi 0.82.0 自身的 compat schema 接受额外属性，插件却统一使用了 `additionalProperties: false`，错误地拒绝了 Pi 能加载的配置。

修正为 compat 对象校验已知字段并保留额外属性，与 Pi 的扩展规则一致；没有针对某个旧字段添加兼容分支，也没有删除用户配置。加载校验失败时，错误消息和结构化错误都包含供应商及字段路径，不包含字段值。新增真实 Pi RPC 启动、模型枚举、编辑后字段保留和错误定位测试。完整 32 项测试及类型检查通过；用户现有 11 个供应商配置只读校验全部通过，配置文件摘要未变化。
